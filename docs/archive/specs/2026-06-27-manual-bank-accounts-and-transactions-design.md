# Manual bank accounts and manual transactions design

## Context

The bank accounts UI now offers a manual-account path alongside automatic bank linking. The first wired slice should let users create a manual account and enter transactions one-by-one. Later bulk imports from CSV, PDF, screenshots, or similar sources should reuse the same storage and review flow rather than create a parallel transaction model.

## Goals

- Create manual bank accounts from the existing "Add transactions yourself" dialog path.
- Let users enter individual signed manual transactions from a manual account page.
- Reuse the existing bank account, bank transaction, Zero query, and transaction-table categorization flow.
- Store manually entered transactions as uncategorized / needs-review rows so users can categorize them later.
- Keep opening balances out of this slice until they have a dedicated design.

## Non-goals

- Bulk import from CSV, PDF, screenshots, email, or bank export files.
- Opening balance entry or automatic opening-balance postings.
- Category selection during manual transaction entry.
- Editing or deleting manual transactions.
- Manual transaction entry for provider-linked bank accounts.

## Data model

Manual accounts reuse the existing `bank_accounts` and bank-linked `ledger_accounts` model:

- `bank_accounts.provider = 'manual'`.
- `bank_accounts.bankConnectionId = null`.
- Provider-specific identifiers are generated by the app using stable manual values, not external provider IDs.
- Sync fields stay idle/null because manual accounts do not sync with GoCardless.
- Each manual bank account gets a linked `ledger_accounts` row with `type = 'bank'` and `linkedBankAccountId = bank_accounts.id`.

Manual transactions reuse `bank_transactions`:

- `providerTransactionId` is generated by the app.
- `status = 'booked'`.
- `amount` is parsed from a signed decimal user input into the canonical scale-4 integer money format.
- `currency` comes from the manual bank account.
- `raw` can store a small app-owned marker/source payload for manual provenance.
- No `ledger_transactions` or `ledger_postings` are created at entry time.

Because no ledger interpretation is created during entry, existing dashboard logic should show manual transactions as uncategorized / needing review. Later categorization uses the current bank-import categorization path and creates the balanced ledger interpretation.

## User flow

### Create a manual account

From Bank accounts → Connect bank → Add transactions yourself:

- The manual account form becomes active.
- Fields:
  - Account name
  - Account type
  - Currency
  - Notes
- The opening balance field is removed or hidden.
- Saving creates the manual bank account and linked bank ledger account.
- After save, the dialog closes and navigates to the new manual account page so the user can add transactions immediately.

### Enter a manual transaction

On `/app/bank-accounts/$bankAccountId`:

- Show an `Add transaction` action only when the selected account is manual.
- The action opens a small dialog/form.
- Fields:
  - Date
  - Description
  - Signed amount
- Account and currency are implicit from the page.
- Category is intentionally omitted; users categorize later in the existing transaction table.

Provider-linked accounts remain sync-oriented and do not show manual transaction entry.

## Mutations and authorization

Because the affected tables are Zero-backed app/domain data, user-facing writes should go through Zero custom mutators.

Add mutators:

- `banking.createManualBankAccount`
- `banking.createManualTransaction`

Server-side mutators must authorize from authenticated Zero context:

- Manual account creation requires access to the target team.
- Manual transaction creation requires access to the target account's team.
- Manual transaction creation must reject non-manual/provider-linked accounts.
- Client-supplied team IDs are not authority by themselves.

Client-side optimistic mutators should:

- Insert the manual `bank_accounts` row and linked `ledger_accounts` row for account creation.
- Insert the manual `bank_transactions` row for transaction creation.
- Use generated client IDs that match the server payload shape enough for a seamless optimistic UI.
- Use `runZeroMutation` so rare server failures toast in the background.

## Validation

Manual account validation:

- Account name is non-empty after trimming.
- Account type maps to the supported bank-like account options for this UI.
- Currency is a 3-letter uppercase code.
- Notes are optional and trimmed into the linked ledger account `description`.

Manual transaction validation:

- Date is a valid `YYYY-MM-DD` date.
- Description is non-empty after trimming.
- Amount is a signed decimal string.
- Parsed amount is non-zero.
- Parsed scale-4 integer amount is a safe integer.
- Currency is inherited from the account.

## Testing

Add tests at meaningful boundaries:

- Domain/server command tests for creating manual accounts and manual transactions, including authorization and linked/provider account rejection.
- Zero mutator tests or focused unit tests for optimistic insertion shape where practical.
- UI tests for:
  - Manual account form is enabled and opening balance is absent.
  - Saving a valid manual account calls the new mutation.
  - Manual account pages show `Add transaction`.
  - Provider-linked account pages do not show `Add transaction`.
  - Manual transaction entry calls the new mutation with signed amount/date/description.
- Existing dashboard/model coverage should prove unreconciled bank transactions render as uncategorized; add a focused regression only if the manual path exposes a gap.

## Future bulk import path

CSV/PDF/screenshot imports should create the same manual `bank_transactions` rows under a manual `bank_accounts` row. Import-specific parsing and deduplication can be layered later around `providerTransactionId`, `raw`, and import metadata without changing the review/categorization UI.
